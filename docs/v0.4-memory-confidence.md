# v0.4 设计细化：Memory Confidence Pipeline

> **状态：设计完成，尚未实现。**  
> **选型理由：** v0.2 已有 soft pref / hypothesis 落库，但缺少「证据 → 置信度 → 确认」状态机；这是 Life Loop 真正长出「个性」的关键，也比先接 Calendar/Gmail 更能拉开和普通 Agent Demo 的差距。多目标权衡、个人知识库等其它 v0.4 项依赖更可信的 Memory，故优先细化本块。

关联：`DESIGN.md`（北星与 Goal Tree）、`ROADMAP.md` §3、现实现 `loop/feedback.py`（`soft:` 前缀、`_hypotheses` 桶）。

---

## 1. 问题定义

当前 v0.2 反馈环会：

- 把 gap 启发写成 `soft:*` 偏好（confidence 封顶 0.6）
- 把文本假设追加到 `preferences["_hypotheses"].items`

缺口：

1. **没有状态机**：hypothesis 与 confirmed 边界模糊，容易「一晚睡差 → 永久规则」。
2. **没有可引用证据**：无法回答「这条偏好凭什么成立」。
3. **Planner / Critic 用法不明**：软偏好该如何影响提案权重、何时必须 HITL 升级。
4. **无法纠错 / 衰减**：用户否认或长期无复现时，如何降级或归档。

本设计要回答：

> Agent 如何从**行为轨迹与 Outcome**学习个人偏好，而不是从**一句话**永久记忆？

---

## 2. 设计目标与非目标

### 目标

- 统一记忆条目生命周期：`observation → hypothesis → confirmed`（可回退）。
- 每条记忆绑定 **Evidence**（outcome / decision / 显式用户陈述）。
- Confidence 有可解释的更新规则；Confirmed 默认需 **重复证据或用户确认**。
- Planner 只把 Confirmed（及高置信 Hypothesis）当 soft prior；Critic 可质疑低证据偏好。
- 与 v0.3 Decision Log 对齐：偏好升降级写入决策痕迹。

### 非目标（本块不做）

- 不实现真实向量库 / 大规模 RAG（留给 Personal Knowledge）。
- 不自动修改 Vision / 长期目标（仍只产出 suggestion）。
- 不做多租户；单用户本地 JSON/SQLite 即可。
- 不在本设计中落地 Calendar 等外部 adapter。

## 3. 领域模型

### 3.1 Evidence

```text
Evidence
  evidence_id: uuid
  kind: outcome | decision | user_utterance | gap_report | manual
  ref_id: string          # outcome_id / decision_id / ...
  observed_at: datetime
  summary: string         # 人可读一句话
  signals: object         # 可选结构化信号，如 {sleep_delta: -1.0}
```

规则：

- 一条记忆可挂多条 Evidence（追加，不覆盖）。
- 删除记忆时 Evidence 可硬删或软归档；审计场景建议软归档。

### 3.2 MemoryEntry（偏好 / 习惯原子）

```text
MemoryEntry
  memory_id: uuid
  key: string             # 稳定键，如 "evening.deep_work.after_22"
  statement: string       # 自然语言：用户通常不在 22 点后安排深度学习
  category: preference | habit | constraint_soft | anti_preference
  status: observation | hypothesis | confirmed | rejected | archived
  confidence: float       # 0.0–1.0
  evidence_ids: [uuid]
  supporting_count: int   # 同向证据次数
  contradicting_count: int
  created_at / updated_at
  last_confirmed_at: datetime | null
  source: life_loop | dialogue | import | critic
  scope: work | life | family | global
  affects: [string]       # 影响面提示，如 ["today_plan","evening_block"]
```

### 3.3 状态机

```text
                    ┌──────────────┐
         evidence   │ observation  │  单次信号 / 弱信号
              ┌────►│              │
              │     └──────┬───────┘
              │            │ ≥1 合理证据 或 明确对话推断
              │            ▼
              │     ┌──────────────┐
              │     │  hypothesis  │  可被 Planner 弱引用
              │     └──────┬───────┘
              │            │
       contradict│   ┌─────┴──────────────────────┐
              │    │ 重复同向证据达阈值 N          │ 用户显式确认
              │    │ 或 时间窗内稳定复现           │
              │    ▼                              ▼
              │  ┌──────────────┐          ┌──────────────┐
              └──┤  confirmed   │◄─────────┤  confirmed   │
                 └──────┬───────┘          └──────────────┘
                        │ 用户否认 / 强反证 / 长期无复现衰减到底
                        ▼
                 ┌──────────────┐
                 │  rejected /  │
                 │  archived    │
                 └──────────────┘
```

建议默认阈值（可配置，写入 `data/memory_policy.json`）：

| 参数 | 默认 | 含义 |
|------|------|------|
| `promote_hypothesis_min_support` | 1 | observation → hypothesis |
| `promote_confirmed_min_support` | 3 | 同向证据次数（不含用户确认捷径） |
| `promote_confirmed_min_confidence` | 0.75 | 自动晋升下限 |
| `user_confirm_sets_confidence` | 0.9 | 用户确认后的置信度 |
| `max_auto_confidence_without_confirm` | 0.7 | 无用户确认时的上限 |
| `contradiction_demote_threshold` | 2 | 反证次数触发降级 |
| `decay_half_life_days` | 60 | 无新证据时置信度半衰期 |
| `planner_min_status_for_prior` | hypothesis | 低于此状态不进 Planner prior |

## 4. Confidence 更新（可解释、可测）

采用**简单可复现**规则，避免黑盒 embedding 打分作为唯一来源：

```text
初始：
  observation: 0.25
  由 gap 启发的 hypothesis: min(0.45 + 0.1 * severity_bonus, 0.6)

同向证据 +1：
  confidence ← min(confidence + 0.12, max_auto_confidence_without_confirm)

反证 +1：
  confidence ← max(confidence - 0.18, 0.05)
  contradicting_count += 1
  若 contradicting_count ≥ threshold → status 降为 hypothesis 或 rejected

用户确认：
  status ← confirmed
  confidence ← user_confirm_sets_confidence

用户否认：
  status ← rejected
  confidence ← 0
  写入 Decision Log（human_feedback）

时间衰减（日批 / 唤醒时）：
  若 now - last_evidence_at > 0：
    confidence ← confidence * 0.5 ** (days / decay_half_life_days)
  若 confirmed 且 confidence < 0.5 → 降为 hypothesis（需记录）
```

**禁止**：单次 Outcome 或单句聊天直接 `confirmed`（除非用户明确说「以后都按这个来」→ 视为确认捷径，仍写 Evidence `kind=user_utterance`）。

## 5. 与现有模块的衔接

### 5.1 Life Loop（`apply_feedback_loop`）

改造方向（实现时）：

1. Gap → 不再直接 `preferences[soft:key]=...`，改为 upsert `MemoryEntry`。
2. `_hypotheses` 桶迁移为 `data/memory_entries.jsonl`（或 SQLite `memory_entries`）。
3. `FeedbackResult` 增加 `memory_upserts: list[MemoryChange]`。

伪流程：

```text
analyze_gaps(outcome)
  → 对每条 soft_preference / hypothesis 建议：
       find_or_create MemoryEntry(key)
       append Evidence(kind=gap_report|outcome)
       bump supporting_count / confidence
       maybe_promote(status)
  → persist
  → DecisionLog.append(action=memory_update, ...)
```

### 5.2 Planner

System prior 组装：

```text
load_memories(status ∈ {hypothesis, confirmed}, confidence ≥ 0.4)
  → 按 scope 过滤当前场景
  → 注入 prompt：「以下为带置信度的个人先验，非硬约束…」
  → Confirmed 权重大于 Hypothesis；observation 默认不注入
```

硬约束仍只来自：睡眠 / 接孩子 / 纪念日 / 用户标注的 `constraint`（未来可另表），**不是**高置信偏好自动升硬。

### 5.3 Critic

新增审阅维度（read-only）：

- 提案是否**过度依赖**低置信记忆？
- 提案是否**违反** confirmed 偏好而无 rationale？
- 是否试图把单次 outcome 写成 confirmed？→ reject / conditional_pass

Critic 输入增加 `active_memories` 摘要；输出 objection code 建议：

- `MEM_LOW_CONFIDENCE_OVERFIT`
- `MEM_CONFIRMED_VIOLATION`
- `MEM_PREMATURE_CONFIRM`

### 5.4 HITL / Decision Log（v0.3）

下列动作 `SafetyLevel` 建议：

| 动作 | SafetyLevel | HITL |
|------|-------------|------|
| 写入/更新 observation、hypothesis | low | 否 |
| 自动晋升 confirmed（达阈值） | medium | 可选通知 |
| 用户确认 / 否认 | medium | 本身即人在回路 |
| 删除 confirmed / 批量导入记忆 | high | 是 |
| 把偏好升为硬约束 | irreversible | 是 |

Decision Log 字段补充：`memory_ids`, `from_status`, `to_status`, `confidence_before/after`。

## 6. 存储布局（实现时）

```text
data/
  memory_entries.jsonl      # 一行一条 MemoryEntry 快照或事件
  memory_evidence.jsonl     # Evidence 追加
  memory_policy.json        # 上表阈值
  preferences.json          # 过渡期：兼容 soft:* ；实现后标 deprecated
```

查询需求：

- 按 `key` upsert
- 按 `status` + `scope` 列出给 Planner
- 按 `evidence.ref_id` 反查（解释「为何这么排今晚」）

首版 JSONL 足够；条目量大后再迁 SQLite，API 不变。

## 8. 端到端场景（验收故事）

### 故事 A：三周后才确认「周一晚不排深度学习」

1. 周一晚 Outcome：学习块未完成 + fatigue↑ → observation。
2. 第二、第三周同类 gap → hypothesis，confidence 爬升但仍 ≤ 0.7。
3. 第三次同向后达 `promote_confirmed_min_support` → **通知用户**「是否确认为稳定偏好？」  
   - 确认 → confirmed 0.9  
   - 忽略 → 保持 hypothesis，不自动 confirmed（若策略要求 HITL）
4. 之后 Planner 排周一晚时降权深度学习；若仍强排，Critic 打 `MEM_CONFIRMED_VIOLATION`（conditional）。

### 故事 B：用户一句话 vs 行为

1. 用户说「我喜欢熬夜学习」→ `user_utterance` evidence，status=hypothesis，confidence=0.5（对话可略高但未确认前不超过 auto cap，或标记 `pending_confirm`）。
2. 连续 Outcome 显示熬夜后 work_progress↓、happiness↓ → contradicting evidence。
3. Critic / Feedback 建议 reject 或改写为「偶发冲刺可接受，不宜常态」。
4. Decision Log 留下反证链，避免「听过一次就永久记忆」。

### 故事 C：衰减

1. Confirmed「冬天早睡」半年无相关证据且季节变化 → decay 后降 hypothesis，Planner 权重下降，避免过期习俗锁死。

## 9. 测试计划（实现时必须有）

- 状态机：非法迁移拒绝（rejected → confirmed 必须经新 evidence + confirm）。
- Confidence 数值：同向/反证/确认/衰减的确定性断言。
- 单次 outcome **不能** confirmed。
- `list_priors` 过滤 observation。
- Life Loop dry-run：三次合成 gap 后出现 promote 候选。
- Decision Log：confirm/reject/auto-promote 各至少一条 trace。

## 10. 与其它 v0.4 项的边界

| 项 | 与本设计关系 |
|----|----------------|
| Multi-objective trade-off | 使用 Confirmed/Hypothesis 作为权重先验；冲突解释引用 memory_id |
| Personal knowledge | 知识条目 ≠ 偏好；知识无 status 机，仅检索；偏好走本流水线 |
| Calendar/Gmail/... | 提供更富 Evidence（实际出行、实际发送），不替代本状态机 |
| Family / Code Agent | `scope=family` / 任务级记忆；仍走同一 MemoryEntry |

建议实现顺序：**Memory Confidence → Multi-objective（Critic 价值冲突）→ Adapters**。
