# v0.3.1 Runtime Trace — ExecutionRecord & Observation

> **Status: design + light schema shipped in v0.3.1.** Full runtime (real tool I/O, adapters) is **not** built. Dry-run creates an `ExecutionRecord` stub before Outcome.

## Pipeline boundary

```
Proposal → ExecutionRecord → Observation → Outcome → Gap → Feedback → Memory
```

| Stage | Meaning |
|-------|---------|
| **Proposal** | What the agent *intends* to do (plan, tool_actions, declared safety). |
| **ExecutionRecord** | What was *actually attempted* (tools invoked, changes, errors, timestamps). |
| **Observation** | Thin note of what was *seen* after attempt (signals). May fold into ExecutionRecord. |
| **Outcome** | Semantic metrics vs expectation (`sleep_hours`, `work_progress`, …). **Not** equal to Action result. |
| **Gap → Feedback → Memory** | Learn conservatively; soft memory stays provisional until v0.4. |

**Outcome ≠ Action result.** A successful tool call can still produce a bad life Outcome (e.g. email sent but sleep cratered). ExecutionRecord captures the attempt; Outcome captures goal-metric consequences.

## Light schema (implemented)

```text
ExecutionRecord
  execution_id, trace_id, proposal_id
  started_at, finished_at
  status: planned | running | succeeded | failed | skipped | dry_run
  tool_actions: list[object]
  actual_changes: list[object]
  errors: list[str]
  observation_notes, observed_signals   # thin Observation fold-in

Observation (optional thin model)
  observation_id, trace_id, execution_id?, proposal_id?
  observed_at, notes, signals
```

Dry-run `run_life_loop_dry` creates an `ExecutionRecord` with `status=dry_run` before writing Outcome, and propagates one `trace_id` across DecisionRecord → ExecutionRecord → Outcome → FeedbackResult.

## Non-goals for v0.3.1

- Real Calendar / Gmail / Weather / Traffic adapters
- Full Observation service / event bus
- v0.4 MemoryEntry confidence pipeline code
